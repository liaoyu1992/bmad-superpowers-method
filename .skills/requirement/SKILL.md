# requirement — 需求规格化（含三道防线 + 平台筛选）

> 阶段一技能。将需求文档转化为结构化的需求规格说明书。

## 执行步骤

### 步骤 0：解析平台筛选指令

从用户输入中解析"只做XX"指令：

| 用户输入 | 解析结果 |
|----------|----------|
| 无平台筛选 | 实施所有识别到的平台 |
| `只做APP` | 实施范围 = [APP] |
| `只做后端` | 实施范围 = [BE] |
| `只做PC` | 实施范围 = [PC] |
| `只做APP+后端` | 实施范围 = [APP, BE] |
| `只做小程序` | 实施范围 = [MP] |

**筛选规则**：
- 需求文档中的**所有平台需求都必须识别和记录**，不遗漏
- 被排除的平台需求仍在 `requirements.md` 中列出，但标记为"本次不实施"
- 后续阶段（planner/backend/frontend）只为实施范围内的平台生成计划和代码
- 跨平台需求（REQ-XP-）：只要涉及的任一平台在实施范围内，就纳入实施

### 步骤 1：读取所有需求文档

读取 `docs/input/converted/` 目录下所有 `.md` 文件。记录每个文件的来源和平台属性。

### 步骤 2：识别平台并拆分需求

识别需求文档涉及的目标平台：

| 平台代码 | 平台名称 | REQ 编号前缀 | 典型内容 |
|----------|----------|-------------|----------|
| BE | 后端 | REQ-BE- | API、服务端逻辑、数据库 |
| PC | PC 客户端 | REQ-PC- | 桌面端页面、PC 专属功能 |
| APP | 移动端 | REQ-APP- | 移动端页面、移动端专属功能 |
| MP | 小程序 | REQ-MP- | 微信/支付宝小程序 |
| XP | 跨平台 | REQ-XP- | 同时影响多个平台 |

**拆分规则**：
- 跨平台功能用 REQ-XP- 编号，同时在各平台分区列出前端消费行为
- 后端 API 同时服务多个前端时，归后端，前端分区只列消费行为
- 不确定平台归属时，列入"待确认平台"分区，**不要擅自归类**
- **所有平台需求都必须识别**，即使被排除在实施范围之外

### 步骤 3：生成需求规格

写入 `docs/specs/requirements.md`，格式要求：

- **用户故事**：作为[角色]，我想要[功能]，以便[价值]
- **验收标准（GWT）**：AC-{平台}-001-01：Given [前置] When [操作] Then [结果]
- **覆盖**：正常流程、异常流程、边界场景
- **【防线 A】**每条 REQ 必须标注原文出处：`> 来源：prd-backend.md §3.2 "用户管理" 第 2 段`
- 禁止"待定"/"TBD"；如信息不足列入"待确认问题清单"
- **【YAGNI】**禁止添加需求文档中未提及的任何功能
- **【平台筛选】**如有平台筛选指令，在 `requirements.md` 头部记录"本次实施范围"：
  ```
  > ## 本次实施范围
  > 实施平台：APP, BE
  > 排除平台：PC（需求已记录，本次不实施）
  > 跨平台需求（REQ-XP-）：涉及 APP 或 BE 的纳入实施
  ```
  每条 REQ 标注实施状态：`[实施]` 或 `[本次不实施]`

### 步骤 4：防线 B — 反向校验

生成 `docs/reports/req-validation-001.md`，执行三项校验：

1. **需求遗漏检查**：逐条扫描原文每个段落 → 检查是否有对应 Spec 条目
2. **需求多余检查**：逐条扫描 Spec → 检查是否有原文依据
3. **平台归属检查**：检查每条 REQ 的平台分类是否正确

输出格式：
```
| 原文位置 | 原文摘要 | 对应 Spec 编号 | 状态 |
| prd.md §1.1 | "用户注册" | REQ-BE-001 | ✅ 已覆盖 |
| prd.md §3.2 | "指纹登录" | — | ❌ 未覆盖 |
```

### 步骤 5：防线 C — 交叉审问

生成 `docs/reports/req-grill-001.md`，用原始需求"审问"Spec：

1. **术语一致性**：Spec 术语与原文一致？
2. **业务规则冲突**：Spec 有互相矛盾的需求？
3. **平台串台**：APP 专属功能误放 PC 分区？
4. **范围溢出**：Spec 添加了原文没有的功能？
5. **范围缺失**：原文要求但 Spec 遗漏？
6. **验收标准可测性**：每条 AC 可否用测试用例验证？

### 步骤 6：加载经验库

- 读取 `docs/learning/LEARNING.md` 索引表
- 匹配"需求分析"或"平台拆分"触发条件
- 如有新经验，追加到 LEARNING.md 并写入 `docs/learning/entries/`

## 完成后

等待人工审批 Gate 1。审批时需查看三个文件：
1. `requirements.md` — 需求规格
2. `req-validation-001.md` — 校验报告（重点看 ❌ 未覆盖、⚠️ 可能多余）
3. `req-grill-001.md` — 审问报告（重点看"需修改"结论）

## 与上下游技能衔接

| 衔接方向 | 说明 |
|----------|------|
| ← `convert-documents` | 读取转换后的 Markdown 需求文档 |
| ← `brainstorm` | 如需求不明确，先由 brainstorm 探索方案 |
| → `architect` | requirements.md 作为 tech-spec 的输入 |
| → `designer` | requirements.md 作为 design-spec 的输入 |
| → `planner` | requirements.md 作为任务拆解的输入 |
| → `backend`/`frontend` | 需求中的 AC 作为 TDD 测试用例的依据 |

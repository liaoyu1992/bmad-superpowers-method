# grill — 交叉审问

> 防线 C 技能。用原始需求"审问"Spec 或代码，发现表面正确但实质有问题的地方。

## 何时使用

| 场景 | 审问对象 | 输入 |
|------|----------|------|
| 阶段一完成后 | requirements.md | 原始需求文档 |
| 阶段二完成后（新项目） | tech-spec + design-spec | requirements.md |
| 阶段二完成后（迭代项目） | tech-spec + design-spec + **现有代码库** | requirements.md + 现有代码 |
| 阶段三完成后 | plans/*.md | requirements + tech-spec + design-spec |
| 阶段五 | 代码 | requirements + tech-spec + design-spec |
| 任何需要"挑战"的时刻 | 任意 Spec/代码/计划 | 对应的上游文档 |

## 审问维度

### 1. 术语一致性

- Spec 中用了"用户"，原文用的是"账户"？
- Spec 中用了"订单"，原文用的是"工单"？
- 同一概念在不同章节名称不统一？

### 2. 业务规则冲突

- Spec 中 A 功能说"需要登录"，B 功能说"免登录"？
- 原文说"24 小时有效"，Spec 写成了"7 天有效"？
- 业务流程中有逻辑矛盾？

### 3. 平台串台

- APP 专属功能（如指纹登录）误放到了 PC 分区？
- 后端 REQ 描述的其实是前端逻辑？
- PC 和 APP 的交互差异被忽略？

### 4. YAGNI 违规

- Spec 中添加了原文未提及的功能？
- 代码中有 Spec 未提及的实现？
- "顺手加了"的功能？

### 5. 范围溢出

- 原文说"支持分页"，Spec 扩展成了"支持游标分页+传统分页+无限滚动"？
- 原文说"导出 CSV"，Spec 加了"导出 Excel + PDF"？

### 6. 范围缺失

- 原文要求"密码强度校验"，Spec 遗漏了？
- 原文要求"操作日志"，代码未实现？

### 7. 验收标准可测性

- AC 写了"系统应快速响应"——"快速"是多少 ms？
- AC 写了"用户友好的错误提示"——怎么测"友好"？
- AC 不可测 = 无效 AC

### 8. 旧代码兼容性（迭代项目）

- 新设计的技术方案与现有代码库的技术栈是否兼容？
- 新 API 是否破坏了现有 API 的调用方？
- 数据模型变更是否需要迁移脚本？
- 新组件是否与现有组件库风格一致？
- 借鉴 BOSS grill-with-docs：带着现有代码/文档挑战方案

### 9. 计划可执行性（阶段三审问）

- 计划中的步骤是否有遗漏的依赖？
- 计划中的验证命令是否正确？
- 计划是否覆盖了所有实施范围内的 REQ？
- 计划步骤是否足够原子化（2-5 分钟内可完成）？

## 报告格式

```markdown
# 交叉审问报告 grill-001

## 审问对象：requirements.md
## 审问依据：原始需求文档

## 发现

| # | 类型 | 严重程度 | 位置 | 审问内容 | 结论 |
| 1 | 术语不一致 | P2 | requirements.md §3.2 | Spec 用"账户"，原文用"用户" | 需修改 |
| 2 | 范围溢出 | P1 | requirements.md §5.1 | Spec 增加了"积分系统"，原文未提及 | 需删除 |
| 3 | AC 不可测 | P1 | AC-PC-002-01 | "快速响应"无量化 | 需修改为"< 500ms" |

## 总结

- 需修改：5 项
- 需删除：2 项
- 需补充：1 项
- 裁定：REQUEST CHANGES
```

## 与上下游技能衔接

| 衔接方向 | 说明 |
|----------|------|
| ← `requirement` | 阶段一完成后审问 requirements.md |
| ← `architect`/`designer` | 阶段二完成后审问 tech-spec + design-spec（含现有代码库） |
| ← `planner` | 阶段三完成后审问 plans/*.md 的可执行性 |
| → `requirement`/`architect`/`designer`/`planner` | 审问发现的问题交回原技能修复 |
| → `review` | 阶段五审问代码，结果交回 review |

# brainstorm — 需求探索与方案收敛

> 借鉴 BOSS /brainstorming 机制。防止"想清楚之前就开写"。

## 何时使用

- 需求文档信息不足以直接生成 Spec
- 技术方案有多种选择，需要权衡
- 用户说"我大概想做个 XX，但还没想清楚"
- 需要对比多个架构/框架/方案

## 执行步骤

### 步骤 1：理解需求边界

读取 `docs/input/converted/` 中的需求文档，提取：
- 明确的功能需求
- 模糊的/待定的需求
- 隐含的约束条件（性能、安全、兼容性等）

### 步骤 2：列出候选方案

为每个模糊点列出 2-3 个候选方案，每个方案包含：

```markdown
## 方案 A：[名称]
- **描述**：一句话概括
- **优势**：
  - ...
- **劣势**：
  - ...
- **适用场景**：...
- **实现复杂度**：低/中/高
- **风险**：...
```

### 步骤 3：方案对比矩阵

生成对比表：

```markdown
| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 开发效率 | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ |
| 性能 | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ |
| 可维护性 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| 学习成本 | ⭐⭐ | ⭐⭐⭐ | ⭐ |
| 社区支持 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
```

### 步骤 4：收敛决策

对每个模糊点给出推荐方案及理由：

```markdown
## 决策：推荐方案 A
**理由**：
1. ...
2. ...
**妥协**：
- 接受方案 A 的 XX 劣势，因为 ...
```

### 步骤 5：输出到文档

将探索结果写入 `docs/reports/brainstorm-001.md`，供后续 `requirement` 和 `architect` 技能参考。

## 与上下游技能衔接

| 衔接方向 | 说明 |
|----------|------|
| → `requirement` | 探索结果作为需求规格化的输入参考 |
| → `architect` | 技术选型决策作为 tech-spec 的输入参考 |
| → `research` | 如需深度技术调研，交接给 research 技能 |

## 与经验库联动

- 读取 `docs/learning/LEARNING.md` 索引表
- 匹配"方案探索"或"技术选型"触发条件
- 如有新经验，追加到 LEARNING.md 并写入 `docs/learning/entries/`

## 使用场景

| 场景 | 示例 |
|------|------|
| 技术选型 | "用 React 还是 Vue？对比一下" |
| 架构方案 | "微服务还是单体？给个建议" |
| 功能取舍 | "这个功能要不要做？分析一下" |
| 需求澄清 | "用户说要一个'报表系统'，太模糊了，先探索" |

# loop — 修复循环

> 借鉴 BOSS /loop 机制。自动迭代直到全绿。

## 触发条件

- `/quality-gate` 返回 FAIL
- `/test` 有失败用例
- `/review` 返回 REQUEST CHANGES 或 BLOCK
- 用户手动触发

## 循环流程

```
┌─────────────────────────────────────────┐
│           /loop 启动                     │
│                                         │
│  ┌─────────┐                            │
│  │ 1.编译   │──── error ───→ 修复编译    │
│  └────┬────┘                            │
│       │ pass                           │
│  ┌────▼────┐                            │
│  │ 2.测试   │──── fail ───→ 修复代码    │
│  └────┬────┘                            │
│       │ pass                           │
│  ┌────▼────┐                            │
│  │ 3.门禁   │──── FAIL ──→ 修复问题      │
│  └────┬────┘                            │
│       │ PASS                           │
│  ┌────▼────┐                            │
│  │ 4.审查   │──── CHANGES → 修复问题     │
│  └────┬────┘                            │
│       │ APPROVE                         │
│  ┌────▼────┐                            │
│  │  全绿！  │                            │
│  └─────────┘                            │
└─────────────────────────────────────────┘
```

## 执行步骤

1. **诊断**：读取最近的质量门禁报告/测试报告/审查报告
2. **提取问题清单**：按严重程度排序（P0 → P1 → P2 → P3）
3. **逐个修复**：
   - 读取问题对应的代码文件
   - 理解问题原因
   - 修复代码
   - 运行对应验证（编译/测试）
4. **重新检查**：修复后重新运行 quality-gate
5. **循环判断**：
   - 全绿 → 退出循环，输出总结
   - 有失败 → 继续修复
   - 达到最大迭代次数 → 输出未解决问题清单，等待人工介入

## 最大迭代次数

**默认 3 轮**。每轮包含：编译 → 测试 → 门禁。

如果 3 轮后仍有未解决问题：
- 输出剩余问题清单
- 标注哪些问题已修复、哪些未修复
- 等待人工介入

## 循环日志

每次循环迭代记录到 `docs/reports/loop-log.md`：

```markdown
# 修复循环日志

## 第 1 轮
- 编译：❌ 2 errors
  - error 1: src/api/auth.ts:42 类型不匹配 → 已修复
  - error 2: src/models/user.ts:15 缺少 import → 已修复
- 测试：❌ 1 failure
  - "should register" 失败 → 已修复（缺少 mock）
- 门禁：FAIL
  - Null 安全：src/api/auth.ts:42 → 已修复

## 第 2 轮
- 编译：✅ 0 errors
- 测试：✅ 全部通过
- 门禁：✅ PASS
- 审查：✅ APPROVE

## 总结
- 总迭代轮数：2
- 修复问题数：4
- 剩余问题：0
- 状态：✅ 全绿
```
